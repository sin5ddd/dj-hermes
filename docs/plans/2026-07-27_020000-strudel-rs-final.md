# strudel-rs — リアルタイム演奏システム最終型（Rust・デュアルデッキ・バークオンタイズ）Implementation Plan

> **For Hermes:** Load the plan-execution-loop skill and implement this plan task-by-task.

**Goal:** Strudel 記法で書かれた「曲ファイル」を、Rust 製 CLI アプリがリアルタイム演奏する。人間はエディタでファイルを編集すると**小節境界でシームレスに反映**され、LLM は HTTP API / MCP からワンショットまたはストリームで演奏を操作できる。曲A・曲Bを同テンポで並行再生可能にし、**ミキサー層**で音量・EQ/フィルター・切替を行う。

**Architecture:**

```
入力面（3系統・すべて同じ Command チャネルへ）
┌─────────────────────────────────────────────────────────┐
│ 人間A: エディタで songs/*.strudel を保存 → notify crate   │
│        が検知 → バー境界でホットリロード                  │
│ 人間B: REPL (rustyline) — デッキ/ミキサー操作コマンド     │
│ LLM  : HTTP API (axum) + MCP (rmcp, stdio→HTTP ブリッジ) │
└──────────────────────┬──────────────────────────────────┘
                       ▼ Command (crossbeam SPSC)
              ┌─────────────────┐
              │  Scheduler      │  バー境界でのみ状態遷移
              │  (audio thread) │  pending_code / pending_song / mixer を管理
              └────────┬────────┘
                       ▼
        Deck A ◄──同一 Transport(共有時計)──► Deck B
        (曲A voices)                          (曲B voices)
                       ▼
              ┌─────────────────┐
              │  Mixer 層       │  A/B 音量フェーダー・EQ/フィルター
              │                 │  クロスフェード / 曲切替
              └────────┬────────┘
                       ▼
                  AudioBackend (CPAL) → 出力 (ALSA)
```

**中核概念:**

- **曲 (Song)**: `.strudel` ファイル1つ = 1曲。複数パターン（トラック）。**Strudel REPL コピペ優先**:
  ```
  // title: techno1
  setcpm(126/4)
  // kick
  $: s("bd*4").gain(0.9)
  // bass
  $: note("c2 c2 eb2 g2").s("sawtooth").lpf(400).gain(0.7)
  // hat
  $: s("hh*8").gain(0.3)
  // lead
  $: note("<c4 eb4 g4 bb4>").s("square").lpf(2000).gain(0.4)
  // pad
  $: note("c3'maj").s("triangle").lpf(800).gain(0.35)
  ```
  `setcpm` = cycles/min（1 cycle = 1 bar → エンジン BPM = cpm×4）。`$:` 直前コメントがトラック名。レガシー `bpm:` / `name: code` も可。
  Strudel 記法をできるだけそのまま流せる方針。**和音記法（`c3'maj` / `c3'maj7` 等）も初期から対応**する。
- **デッキ (Deck)**: Song をロードして鳴らす再生ユニット ×2（A/B = 曲A・曲B）。両デッキは**同一 Transport（共有グローバル時計）**を参照するため、BPM が同じならバーが完全同期する。BPM が違う場合はマスター BPM（Transport 側）に統一される（曲ファイルの bpm は「マスター未設定時の初期値」として扱う）。
- **ミキサー層 (Mixer)**: 曲A/B の「上」に乗る第3の層。担当は (1) A/B それぞれの音量フェーダー (2) EQ・フィルター (3) A/B のクロスフェードおよび曲切替。デッキは「何を鳴らすか」、ミキサーは「どう混ぜて出すか」。
- **バークオンタイズ (Bar-Quantized Transition)**: コード変更・曲切替・ミュート解除などの**状態遷移は、原則次のバー境界で適用**される。audio スレッド内で `global_sample >= target_bar_sample` になった瞬間に pending を current へ差し替える。デモ用途のため、バッファまたぎは**厳密なサンプル精度よりクリック等の事故防止（安全性）を優先**する（詳細は Risks #1）。
- **クロスフェード (XFade)**: ミキサー層の `xfade N` で N バーかけて A↔B をフェード。等パワーカーブ（`gainA=cos(θ)`, `gainB=sin(θ)`, θ=0..π/2）。フェードもバー境界で開始。
- **LLM ストリーム操作**: HTTP の SSE (`/events`) で状態を購読＋`PUT` 系で操作。加えて **MCP server（rmcp crate, stdio transport）**を `strudel-rs mcp` サブコマンドで起動し、Hermes からツール呼び出し可能にする。**MCP は本体 HTTP への薄いブリッジ**（演奏プロセスは手動起動。stdio 直結で audio を多重起動しない）。

**Tech Stack:** Rust stable / cpal / axum + tokio / rmcp（MCP）/ notify（ファイル監視）/ rustyline / crossbeam / serde+toml は使わず独自ミニパーサ（依存最小）。Linux ターゲット、依存システムライブラリは ALSA のみ。

**音源・エフェクトの位置づけ（重要）:**  
cpal は **音声デバイスへの入出力（コールバックで f32 バッファを埋める）だけ**を担当する。Strudel の Synths / Effects / Samples に相当する処理は **すべて自前 DSP**（`synth.rs` / サンプル再生 / `mixer.rs`）として audio コールバック内（またはその直前のレンダリング）で行う。WebAudio や SuperCollider は使わない。対応範囲の段階定義は後述 **「Strudel 音源・エフェクト対応方針（cpal 実装）」** を参照。参照ドキュメント: [Synths](https://strudel.cc/learn/synths/) / [Effects](https://strudel.cc/learn/effects/) / [Samples](https://strudel.cc/learn/samples/)。

**リポジトリ構成:**
```
strudel-rs/
├── Cargo.toml          # workspace: [strudel-rs(bin), strudel-mcp(bin)] でも単一bin+サブコマンドでも可→単一bin採用
├── src/
│   ├── main.rs         # エントリ: サブコマンド分岐 (play / mcp / list)
│   ├── backend.rs      # AudioBackend trait + NullBackend（cpal 実装はここ）
│   ├── transport.rs    # 共有時計 (BPM, bar 計算)
```

## 可視化: Punchcard / Pianoroll（CLI 実現性調査）

参照: [Visual Feedback - Punchcard / Pianoroll](https://strudel.cc/learn/visual-feedback/)（スクリーンショット相当の機能）

### Strudel 本体がやっていること

| 関数 | 挙動 |
| --- | --- |
| `pianoroll` / `_pianoroll` | パターンを **その時点の評価結果** としてピアノロール風に描画 |
| `punchcard` / `_punchcard` | その後に付く変換（例: 後段の `.color`）も可視化に反映。ミニ記法ハイライトと同じイベント列を再利用するため **軽量** とされる |
| プレフィックス無し | ページ背景に描画 |
| `_` プレフィックス | コード行の直下（インライン）に描画。複数可 |

描画データは概ね:

- 横軸: 時間（cycles、既定 4 サイクル表示、playhead 位置など）
- 縦軸: ノート値（MIDI 相当、`minMidi`/`maxMidi`/`autorange`）
- 各イベント: 開始・長さ・音高・（任意）色・active/inactive
- オプション多数: `labels`, `vertical`, `flipTime`, `smear`, `fold`, active/inactive 色 など

音声 DSP とは独立した **イベント列の可視化** である（`_scope` / `_spectrum` のような波形解析とは別系統）。

### CLI / 本プロジェクトでの実現可否

**結論: 実現可能。** ただしブラウザ Canvas の見た目そのものではなく、**端末上の TUI（または簡易テキスト）近似**になる。

| 方式 | 実現性 | 見た目 | 備考 |
| --- | --- | --- | --- |
| **A. 端末 TUI**（ratatui + crossterm 等） | 高い | ブロック文字 + ANSI 色で矩形ノート | 推奨。Windows Terminal / 現代的 Linux 端末向け |
| B. プレーンテキストダンプ | 非常に高い | `█` や `#` の静止画・バー更新 | 依存ゼロ。デモ用最低限 |
| C. SVG/PNG 書き出し | 高い | ブラウザに近い | リアルタイム性が弱い。展示補助向き |
| D. 埋め込み WebView | 低い〜中 | 本物に近い | 依存・起動が重い。CLI 方針と乖離 |
| E. エディタ内インライン（`_punchcard`） | **不可に近い** | — | ブラウザ IDE 専用。外部エディタに差し込めない |

**「できそう」の根拠:**

1. **データは既にある** — Task 6 の `events(node, cycle)` と Deck のスケジュール結果（start/end/value/Hz）が、ロールのノート矩形そのもの
2. **Transport の playhead** — `bar_pos` / `global_sample` で縦線位置を更新できる
3. **描画負荷は軽い** — オシロ（scope）や FFT（spectrum）よりはるかに安い。audio スレッド外で「直近 N バーのイベント snapshot」を読めば足りる
4. **`.color("cyan")`** — パースしてメタに載せ、TUI の fg 色にマップすれば画像のデモに近い

**主な制約・設計論点:**

1. **REPL との端末競合** — rustyline とフルスクリーン TUI は同時に取り合いやすい  
   - 案1: `strudel-rs play --viz` で **画面分割**（上: ロール、下: 1 行コマンド or キーバインド操作）  
   - 案2: 別プロセス / 別端末で `strudel-rs viz` が HTTP SSE `/events` を購読して描画のみ  
   - 案3: ロールは **数 Hz で画面下部に差分更新**、REPL は通常どおり（ちらつきに注意）
2. **インライン `_punchcard()` は再現しない** — 曲ファイルでは `# viz: punchcard` や REPL `:viz on` / トラック単位フラグで代替
3. **pianoroll vs punchcard の差** — 初期は「Engine が実際に鳴らす最終イベント列」を描く（＝演奏と一致 = punchcard 寄り）。中間パターン専用の pianoroll は後回しで可
4. **解像度** — 端末の行列数に合わせて縦（音域）を fold/autorange。細かい半音は行が足りないと潰れる → `autorange` + アクティブ音域のみ表示が実用的
5. **ステレオ/パンや jux の視覚** — 初期非対応でよい（ノート矩形のみ）

## Strudel 音源・エフェクト対応方針（cpal 実装）

参照（公式）:

- Synths: https://strudel.cc/learn/synths/
- Effects: https://strudel.cc/learn/effects/
- Samples: https://strudel.cc/learn/samples/

### cpal の役割（誤解防止）

| 層 | 担当 | 実装場所の目安 |
| --- | --- | --- |
| **I/O** | デバイスオープン、サンプルレート、コールバックで `&mut [f32]` を埋める | `backend.rs` + cpal |
| **時計** | BPM・バー・global_sample | `transport.rs` |
| **パターン→イベント** | mini 記法評価、メソッドチェーン | `mini.rs` / `code.rs` |
| **音源** | オシレータ / ノイズ / サンプル再生 | `synth.rs` / `sample.rs` |
| **パーボイス FX** | ADSR, lpf/hpf, gain, speed 等（イベントごと） | Voice 内 |
| **バス FX / 切替** | A/B フェーダー, EQ, xfade（必要なら delay/room） | `mixer.rs` |
| **テスト** | デバイス無しで同じ DSP を回す | `NullBackend` |

**Strudel 本体はブラウザの WebAudio グラフ。** 本プロジェクトは同等のグラフを Rust で薄いサブセットとして実装し、最終ミックスだけ cpal に渡す。cpal にシンセ API はない。

デモ用途のため **Strudel 全機能の再実装は目標にしない。** 以下のティアで切り、Task 1–22 は主に **ティアA** を満たせば完了とする。

### Sound 名の解決（Risks #2 確定）

Strudel では `s` / `sound` が **サンプルとシンセの両方**を指す（言語面は共通、エンジンは別）。

本実装の解決順:

```
resolve_sound(name):
  1. 固定波形リストに name がある → Synth(Wave|Noise)
  2. SampleBank に name がある     → Sample(name)
  3. どちらも無い                 → Error（"unknown sound: {name}"。波形でもサンプルでもない、と明示）
```

- **波形優先**（リストが短いため衝突 practically ほぼ無し）
- `note("c3").s("bd")` はサンプルを **音程付き**で再生可能（基準ピッチはサンプル側デフォルト C またはメタデータ。初期は「A4=440 相対で speed 換算」など単純ルールで可）
- `s("bd sd")` は各イベント値が sound 名 → 同じ `resolve_sound`
- タイポ時は「波形リストに無くサンプルにも無い」を一文で返す

初期波形リスト（ティアA）:

`sine`, `sawtooth`/`saw`, `square`, `triangle`/`tri`, およびノイズ `white`, `pink`, `brown`（Strudel [Synths](https://strudel.cc/learn/synths/) の Basic Waveforms + Noise の最小セット）

### Synths — Strudel 機能と実装方針

出典: [strudel.cc/learn/synths](https://strudel.cc/learn/synths/)

| Strudel 機能 | 概要 | ティア | cpal 側の実装メモ |
| --- | --- | --- | --- |
| Basic waveforms | sine / sawtooth / square / triangle | **A** | 位相累積オシレータ。audio スレッドで `phase += freq/sr`。アンチエイリアスはデモではナイーブで可（必要なら後で polyBLEP） |
| デフォルト sound | note のみのとき triangle | **A** | `PatternCode.sound` デフォルト `"triangle"` |
| Noise white/pink/brown | ノイズ音源 | **A** | white=一様乱数、pink/brown は簡易フィルタ（Paul Kellet 等の短い IIR で十分） |
| `noise` パラメータ | オシレータにピンクノイズ混入 | B | Voice に mix 係数 |
| `crackle` + density | クラックル | C / 非対応可 | 優先度低 |
| `partials` / `phases` / `user` | 加算合成 | C | コスト高。デモ非必須 |
| `vib` / `vibmod` | ビブラート | **B** | `freq *= 2^(semitone*sin(2π·f_vib·t)/12)` |
| FM (`fm`, `fmh`, envelope) | FM 合成 | **B** | 簡易 1 オペレータ: `car = sin(2π·(fc+fm_idx·sin(2π·fmh·fc·t))·t)`。フル 8op はしない |
| Wavetable `wt_*` | 1 周期波形ループ | C | サンプル loop の特殊ケースとして後付け可 |
| ZZFX `z_*` | ゲーム向けシンセ | **非対応** | 別エンジン。パースで未知 sound として落とす |

**ティアA の Voice 信号（1 サンプル）概略:**

```
osc/noise →（optional 簡易 FM/vib は B）→ amp ADSR → gain
         → one-pole or biquad LPF（.lpf）→ ボイス出力
```

ADSR は Strudel [Effects - Amplitude Envelope](https://strudel.cc/learn/effects/) の `attack`/`decay`/`sustain`/`release`（および `.adsr("a:d:s:r")`）をティアAでサポートする。現状プランの「短いアタック + 末尾リリース」は仮実装であり、Task 8 で正規 ADSR に寄せる。

### Effects — シグナルチェーンと配置

出典: [strudel.cc/learn/effects](https://strudel.cc/learn/effects/)（公式のローカル FX 順序・orbit の説明）

Strudel の概念:

- **Local effects:** イベント（ボイス）ごとに独立チェーン。同じメソッドを二度書いても **上書き**（直列の二段 lpf にはならない）
- **Global effects:** orbit 単位で共有（delay / room など）。パラメータの取り合いに注意

本プロジェクトへの写像:

```
[Deck A tracks] → voices (local FX) ─┐
                                     ├→ Mixer: gain_a/b, channel EQ/filter, xfade → cpal
[Deck B tracks] → voices (local FX) ─┘
```

| Strudel FX | 種別 | ティア | 実装メモ（Rust/cpal） |
| --- | --- | --- | --- |
| `gain` / `velocity` | local | **A** | 乗算。velocity は gain に掛ける |
| `attack`/`decay`/`sustain`/`release` / `adsr` | local | **A** | Voice 状態機械。秒単位 → サンプル数は `sr` で換算 |
| `lpf` / `lpq` | local | **A**（lpq は B でも可） | ティアA は one-pole LPF で cutoff のみでも可。共振が要るなら biquad |
| `hpf` / `hpq` | local | **B** | biquad HPF |
| `bpf` / `bpq` | local | **B** | biquad BPF |
| `ftype` (12db/ladder/24db) | local | C | フィルタ次数。初期は 1 種類で固定 |
| filter env (`lpa`…`lpenv`) | local | **B** | cutoff を ADSR で変調 |
| pitch env (`penv` 等） | local | **B** | freq を半音オフセットで変調 |
| `pan` | local | **B** | ステレオ化時。初期モノラル出力なら no-op または将来用フィールド |
| `jux` / `juxBy` | パターン | C | パターン変換が本体。音響より mini 側 |
| `coarse` / `crush` / `distort` | local | C | ビットクラッシュ等。デモ非必須 |
| `tremolo*` | local | C | LFO→gain |
| `compressor` | local/orbit | C | コストとチューニングが重い |
| `delay` / `delaytime` / `delayfeedback` | **global** | **C** | Mixer または簡易 orbit バッファ（円環バッファ）。feedback&lt;1 を強制 |
| `room` / `roomsize` 等 | **global** | **C** | 本格 IR は重い。簡易 schroeder/freeverb 風 or 短 IR 1 本 |
| `phaser*` | global/local | C | |
| `duck` / orbit | global | C | サイドチェーン。デモ非必須 |
| `orbit` | global 文脈 | C | 初期は全ボイスが Mixer 直結（orbit=1 相当） |
| Mixer の A/B フェーダー・EQ・xfade | （本プロジェクト独自） | **A** | Strudel の `xfade` パターン関数とは別物。DJ 用バス処理 |

**パーボイス vs ミキサーの切り分け（確定方針）:**

- **曲・トラック由来**の `.lpf` `.gain` `.adsr` 等 → Voice（local）
- **演奏操作由来**の A/B 音量・チャンネル EQ・曲切替 xfade → Mixer
- 同一パラメータを両方で持つ場合: `final = voice_out * track_gain * mixer_fader` のように **直列乗算**し、上書き関係をドキュメント化

```bash
#!/usr/bin/env bash
# 使い方:
#   ./hermes_push.sh code 'note("c3 e3 g3").s("sawtooth")' [A|B]
#   ./hermes_push.sh load songs/techno1.strudel A
#   ./hermes_push.sh xfade B 4
#   ./hermes_push.sh bpm 126
#   ./hermes_push.sh mute A kick / unmute A kick
#   ./hermes_push.sh hush
#   ./hermes_push.sh status
#   ./hermes_push.sh watch        # SSE 状態監視
set -euo pipefail
API="${STRUDEL_API:-http://127.0.0.1:17878}"
j() { python3 -c 'import json,sys; print(json.dumps(json.loads(sys.argv[1])))' "$1"; }

case "${1:-}" in
  code)   curl -s -X PUT -H 'Content-Type: application/json' \
            -d "$(python3 -c 'import json,sys;print(json.dumps({"code":sys.argv[1],"deck":sys.argv[2] if len(sys.argv)>2 else "A"}))' "$2" "${3:-A}")" \
            "$API/code"; echo ;;
  load)   curl -s -X POST -H 'Content-Type: application/json' \
            -d "{\"path\":\"$2\",\"deck\":\"${3:-A}\"}" "$API/song/load"; echo ;;
  xfade)  curl -s -X POST -H 'Content-Type: application/json' \
            -d "{\"to\":\"$2\",\"bars\":${3:-4}}" "$API/xfade"; echo ;;
  bpm)    curl -s -X POST -H 'Content-Type: application/json' -d "{\"bpm\":$2}" "$API/bpm"; echo ;;
  mute)   curl -s -X POST -H 'Content-Type: application/json' \
            -d "{\"deck\":\"$2\",\"track\":\"$3\",\"muted\":true}" "$API/mute"; echo ;;
  unmute) curl -s -X POST -H 'Content-Type: application/json' \
            -d "{\"deck\":\"$2\",\"track\":\"$3\",\"muted\":false}" "$API/mute"; echo ;;
  hush)   curl -s -X POST "$API/hush" -o /dev/null -w 'hushed (%{http_code})\n' ;;
  status) curl -s "$API/status" ;;
  watch)  curl -sN "$API/events" ;;
  *)      sed -n '2,10p' "$0"; exit 1 ;;
esac
```

## Risks / Open Questions

### 1. バッファまたぎのバー境界 — ✅ 確定（安全性優先）

**内容:** バー境界がオーディオバッファ（~5ms）の途中に来る場合、pending 適用タイミングをどうするか。

**決定:** デモ用ツールのため、**サンプル精度の厳密さより安全性（クリック・ノイズ・二重適用事故の回避）を優先**する。

**実装方針:**

- バッファ内スプリット（境界前後でコールバックを分割）は**行わない**
- pending 適用は「そのバッファ処理の先頭 or 末尾のどちらか一方」に寄せ、同一バッファ内で二度適用しない
- 状態差し替え時は既存どおり短時間（例: 5ms）のゲインランプでポップを抑える
- ずれは最大 1 バッファ分を許容する（体感上の小節感は十分）

---

### 2. sound 名の解決（波形 vs サンプル） — ✅ 確定（波形リスト → サンプルへフォールバック）

**内容:**  
`s("bd")` と `s("sawtooth")` は **見た目が同じ API** だが、Strudel 内部ではシンセとサンプルは別エンジン。表記だけ見ると `bd` が波形かサンプルか判別できない。

**これは Rust の型を分ける話ではない。** sound 名文字列の **解決順序** の話。

**決定:**

```
1. 固定波形リスト（sine/sawtooth/square/triangle + white/pink/brown 等）に存在する → シンセ
2. なければ SampleBank を探す → サンプル
3. どちらも無い → 明示エラー（現行曲は継続）
```

- **波形優先**（リストが短く、名前衝突 practically ほぼ無い）
- `note("c3").s("bd")` も **初期から可**（サンプルを pitch/speed で再生）
- `note("c3 e3").s("sawtooth")` は波形シンセ
- `s("bd sd hh")` は各イベント値を同じ `resolve_sound` に通す
- 先頭が `note` か `s` かは「パターン内トークンが音名か sound 名か」の別問題（併用可）

**デメリット（許容）:**

- 将来シンセ名を増やしてサンプルと同名になると衝突（波形優先で固定）
- タイポ時は両方失敗してからエラー（メッセージで「波形でもサンプルでもない」と書く）

詳細テーブルは **「Strudel 音源・エフェクト対応方針」** を参照。

---

### 3. 和音記法（`c3'maj7` 等） — ✅ 確定（初期から対応）

**内容:** 当初プランは「和音記法は非対応・展開済み音名のみ」としていた。

**決定:** Strudel 記法をそのまま流すことも想定するため、**和音記法を最初から対応**する。

**実装方針（Task 7 拡張）:**

- `note_to_hz` の前段で `c3'maj` / `c3'min` / `c3'maj7` 等を **半音オフセット列に展開**し、同時発音（複数 Voice）またはイベント列に落とす
- 対応するコード種は初期セットを明示（例: maj, min, maj7, min7, dim, aug, sus2, sus4）。未対応トークンはパースエラーで現行曲継続
- 曲ファイル例（ambient 等）に和音記法を残してよい（展開済み必須にしない）
- 詳細トークン表は実装時に Strudel / Tidal 系の慣例を参照して Task 7 に固定する

---

### 4. MCP ブリッジ方式 — ✅ 確定（stdio 直結しない）

**内容:** MCP を演奏プロセスに直結するか、HTTP ブリッジにするか。

**決定:**

- **演奏 CLI の起動は手動**（ユーザーまたは展示手順で `./strudel-rs` を先に起動）
- **MCP は HTTP への薄い転送層**（`strudel-rs mcp` が stdio で Hermes と話し、本体 `127.0.0.1:17878` に中継）
- stdio 直結（in-process で audio まで持つ）は**採用しない**。Hermes が MCP を複数回起動したときに **音声デバイス・Transport が多重起動**して厄介になるため

**結果として許容するもの:**

- 本体未起動時、MCP ツールは接続エラーを返す（仕様）
- MCP プロセスのクラッシュは演奏に影響しない（望ましい分離）

### 5. 曲A / 曲B / ミキサー層の 3 層構成 — ✅ 確定（旧「BPM 差の切替」を再定義）

**旧論点:** デッキ間で BPM が違う曲を載せると共有 Transport のせいで位相が崩れる。

**決定（構成）:** 実質 **3 層**にする。

| 層 | 役割 |
| --- | --- |
| 曲A（Deck A） | Song のロード・パターン評価・ボイス生成 |
| 曲B（Deck B） | 同上（並行再生可能） |
| **ミキサー層** | A/B **音量フェーダー**、**EQ・フィルター**、**A/B クロスフェードおよび曲切替** |

**意味:**

- デッキ側は「曲を鳴らすユニット」、ミキサー側は「混ぜて・整えて・切り替える」
- `xfade` / マスター的な A-B 切替 / チャンネル EQ は **mixer.rs** に寄せ、Deck の `gain` と責務を分離する
- Task 14 は「デュアルデッキ + Mixer」に読み替える（ファイル `mixer.rs` を追加）

**BPM について（旧リスクの残部）:**

- 両デッキは引き続き **共有 Transport（マスター BPM）** を見る
- 曲ファイルの `bpm` はマスター未設定時の初期値
- 異なる BPM 想定の曲を同時に「各曲固有テンポ」で鳴らすことはしない（デモ運用は同 BPM またはマスターに追従）

### 6. rmcp crate の API 安定性 — 📌 実装リスク（MCP「規格」そのものではない）

**内容:** MCP（Model Context Protocol）という**通信規格**の話ではなく、Rust から MCP サーバを実装するときに使う **ライブラリ `rmcp` の API がバージョン間で変わりうる**、という実装リスク。

**背景:**

- MCP 規格自体は JSON-RPC ベースのプロトコル
- 本プランは `rmcp` crate（`#[tool]` マクロ、stdio transport 等）でサーバを書く想定
- エコシステムが若いため、マイナーバージョンでもマクロ形状・feature 名・型名が変わることがある

**方針:**

- Task 18 着手時に crates.io / ドキュメントで **ピン留めバージョン**を決める
- マクロが合わない・ビルドが通らない場合は「詰まりプロトコル」: (a) バージョン固定で直す (b) 手書き JSON-RPC の最小 stdio サーバに退避、のどちらか
- ブリッジ設計（#4）のおかげで、MCP 実装の作り直しが演奏コアに波及しにくい

**ユーザー向け一言:** 「MCP のルールが曖昧」というより「Rust 用 MCP ライブラリの書き方がまだ落ち着いてないかも、という注意書き」。
